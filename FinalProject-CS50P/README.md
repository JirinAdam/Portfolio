# 🔐 Password & Passphrase Security Toolkit

#### Video Demo: <https://youtu.be/P8OfMzIXJEs>

#### Description:

The **Password & Passphrase Security Toolkit** is a comprehensive application (command-line interface and a desktop GUI called **PASSMAN**) designed to help users generate secure passwords, create memorable passphrases, and analyze the security of their existing credentials. This project was developed as a final project for CS50, combining cryptographic principles with practical security assessment tools.

## 🎯 Project Overview

In today's digital world, password security is paramount. This toolkit addresses three critical needs:

1. **Generating cryptographically secure random passwords** with customizable character sets.
2. **Creating memorable Diceware passphrases** using the EFF Large Word List.
3. **Analyzing existing passwords** for strength and checking against known data breaches.

The application calculates **entropy** (a measure of password randomness) and estimates crack times for online, GPU-farm and quantum (Grover) attacks. Password length is checked against the public standards **NIST SP 800-63B-4** and **OWASP ASVS 5.0**, and existing passwords are checked against known breaches via **Have I Been Pwned**.

## 📄 File Descriptions

### `project.py`

The main module serving as the application's entry point. It contains the core orchestration logic and reusable analysis functions:
- **`evaluate_entropy`**: Calculates bits via the formula length × log₂(charset_size).
- **`rate_strength`**: Classifies strength into 9 categories based on entropy thresholds.
- **`calculate_crack_time`**: Estimates brute-force resistance against various attack speeds.
- **`calculate_quantum_crack_time`**: Estimates the Grover-based quantum attack time.
- **`check_length_policy`**: Checks length against NIST SP 800-63B-4 and OWASP ASVS 5.0.

**Design Decision:** I chose to centralize all entropy and rating logic here to maintain a single source of truth. The generator and checker classes import these functions rather than reimplementing them, strictly following the **DRY (Don't Repeat Yourself)** principle.

### `generators/password_gen.py`

Contains the `PasswordGenerator` class. It allows for customizable character sets (uppercase, lowercase, digits, symbols). The CLI requires at least two character types - this is my own design choice, not a standard: NIST SP 800-63B-4 and OWASP ASVS 5.0 impose no composition rules and put length first.

**Design Decision:** I debated between using the standard `random` library versus `secrets`. I chose `secrets` because it provides access to the operating system's most secure source of randomness, which is critical for cryptographic applications, whereas `random` is deterministic and unsuitable for security.

### `generators/passphrase_gen.py`

Contains the `DicewareGenerator` class. It utilizes the EFF Large Word List (7,776 words) to create passphrases. Each word adds ~12.9 bits of entropy. The Diceware method was selected because it balances high security with memorability; a 6-word passphrase (~77.5 bits) is stronger than complex 12-character passwords but significantly easier for humans to recall.

### `generators/password_checker.py`

This module handles the analysis of existing credentials loaded from `passwords.csv`. It calculates local entropy metrics and integrates with the **Have I Been Pwned (HIBP)** API.

**Design Decision:** Privacy was a priority. I implemented the **k-Anonymity** model for the API integration. The tool hashes passwords using SHA-1 and sends only the first 5 characters of the hash to the API. This ensures the user's actual passwords are never transmitted over the network.

### `gui.py`

A thin **CustomTkinter** desktop front-end (PASSMAN, 450 × 590 px, Deep Ocean colour palette) over the same logic - it contains no calculations of its own, it only collects input and displays the results of `project.py` and the `generators` package. Three views:
- **Password** - length (slider or typed number, 8-64) and character types; shows entropy, rating and online / GPU-farm / quantum crack times.
- **Passphrase** - number of words (4-12) and separator; same analysis.
- **Check CSV** - runs the HIBP check on `passwords.csv` (or any CSV picked with **Choose CSV**) in a background thread; results table with a horizontal scrollbar, breach and GPU-crackable alerts below it.

Features:
- **Copy** puts the generated secret on the clipboard and clears it after 30 seconds - but only if the clipboard still holds that secret, so anything copied in the meantime is left alone.
- Passwords in the results table are masked by default; the **Show passwords** switch reveals them.
- Rating badges and the strength bar use a colour scale from red (CRITICAL-WEAK) through orange (MODERATE-GOOD) to ocean blues (STRONG-MAXIMUM); green is left out on purpose.
- The passphrase view warns above 10 words ("Very long, but very secure."); the password view enforces the same rules as the CLI (length ≥ 8, at least two character types).

**Design Decisions:**
- The whole window body scrolls vertically, so nothing is cut off on small screens; mouse wheel and touchpad work anywhere over the window (Shift + wheel or a horizontal swipe scrolls the results table).
- Wheel bindings live on a plain `tkinter.Canvas`: CustomTkinter widgets deliberately disable `bind_all` / `unbind_all` and raise `AttributeError`.
- Touchpads send many small wheel deltas instead of 120 per notch, so deltas are accumulated rather than rounded to zero.
- A `--windowed` executable has no console (`sys.stdout` is `None`). `gui.py` redirects output to `os.devnull` with **UTF-8** encoding - with the Windows default cp1252 the first `print("✓ ...")` from the shared CLI code would crash - and shows any unexpected error in a dialog instead of failing silently.

### `test_project.py`

A test suite using `pytest`. It covers entropy calculation, all nine strength ratings, classical and quantum crack-time calculations, and the length-policy check.

## 🔧 Technical Implementation

### Entropy Calculation

Password entropy is calculated as:

$$E = L \times \log_2(C)$$

Where **E** is entropy in bits, **L** is length, and **C** is the pool of unique characters available (26 lowercase + 26 uppercase + 10 digits + 32 symbols from `string.punctuation` = 94 printable ASCII characters).

This is the standard brute-force model: it assumes random characters. Human-chosen passwords (words, patterns like `qwerty`) are weaker than their calculated entropy, which is why the breach check matters.

### Strength Classification

| Entropy (bits) | Rating | GPU farm time at the upper bound (10¹⁵ guesses/s) |
|---|---|---|
| < 32 | CRITICAL | instant |
| 32-40 | VERY WEAK | < 1 ms |
| 40-50 | WEAK | < 1 s |
| 50-63 | MODERATE | ~1.3 hours |
| 63-70 | GOOD | ~7 days |
| 70-80 | STRONG | ~19 years |
| 80-100 | VERY STRONG | ~20 million years |
| 100-128 | EXCEPTIONAL | beyond practical |
| 128+ | MAXIMUM | ≥ AES-128 key strength |

**Note:** These thresholds are my own heuristic. NIST SP 800-63B-4 and OWASP ASVS 5.0 define no entropy levels (and password strength has nothing to do with NIST authentication assurance levels AAL1-3). The only fixed reference points used are the EFF Diceware passphrases (4 words ≈ 51.7 bits, recommended 6 words ≈ 77.5 bits) and AES-128 (NIST post-quantum security category 1).

The security alert in the checker flags every password rated CRITICAL to MODERATE (< 63 bits = about one hour or less for the GPU farm).

### Standards Check (length)

| Length | NIST SP 800-63B-4 | OWASP ASVS 5.0 (6.2.1) |
|---|---|---|
| < 8 | below minimum | below minimum |
| 8-14 | allowed only as part of MFA | meets minimum, 15+ strongly recommended |
| 15+ | meets the single-factor minimum | meets recommendation |

Both standards also require checking new passwords against breached/common password lists, which this toolkit does with HIBP.

### Attack Scenarios

The toolkit estimates crack times based on three threat models:
1. **Online Attack**: 7,200 attempts/day (simulating aggressive rate-limiting). T = (2^E / 2) / S
2. **GPU Farm**: 10¹⁵ guesses/second against a fast hash such as MD5 (future-proof rate: one RTX 5090 does ~220 GH/s on MD5, so this is ~4,500 GPUs - state-actor scale). Slow hashes like bcrypt are millions of times slower to attack. T = (2^E / 2) / S
3. **Quantum**: Grover's algorithm needs ~(π/4)·√N iterations, so T = (π/4) · 2^(E/2) / S with S = 10⁷ iterations/second. There is no "average half" shortcut as in classical search. In practice Grover parallelizes poorly (p machines give only √p speed-up), so this is an optimistic upper bound for the attacker.

## 📦 Standalone Windows app (.exe)

The GUI can be packaged with **PyInstaller** into an app that runs without Python or an IDE. Run in PowerShell from the project folder with the virtual environment active:

```powershell
pip install pyinstaller
taskkill /F /IM PASSMAN.exe   # close a running PASSMAN first, otherwise the build fails with "Access is denied"
pyinstaller --onedir --windowed --clean --noconfirm --name PASSMAN --paths . --add-data "eff_largelist.csv;." --add-data "passwords.csv;." --collect-all customtkinter gui.py
dist\PASSMAN\PASSMAN.exe
```

The result is the folder `dist\PASSMAN\` (`PASSMAN.exe` + `_internal\`) - copy the whole folder to distribute it. Rebuild after every change to the code; the .exe contains a frozen copy of it.

What each option is for:
- `--onedir` instead of `--onefile`: a one-file build unpacks itself to `%TEMP%` on every start, which antivirus software (Avast here) can interfere with - symptom: *"Failed to import encodings module"*. One-dir also starts faster. The first start after a build may still pause while the antivirus scans it.
- `--windowed`: no console window.
- `--clean`: ignore PyInstaller's cache; without it an old analysis can be reused (symptom: *"No module named 'project'"*).
- `--paths .`: lets PyInstaller find `project.py` and the `generators` package.
- `--add-data "...;."`: bundles the word list and the sample CSV next to the code (`;` is the Windows separator).
- `--collect-all customtkinter`: bundles CustomTkinter's themes and assets.

Troubleshooting: if the build still contains old code, check that `gui.py` is not open in an editor with autosave that writes an older copy back to disk. The `build\`, `dist\` and `PASSMAN.spec` files are build output and can be deleted at any time; `build\` and `dist\` are in `.gitignore`, so the .exe is not part of the repository - build it locally.
